# 独自機能一覧の執筆・更新規則

`diff.md` は Misskey-Tempura と本家 Misskey の機能差分を利用者に説明する単一ソースです。アプリ内の `/tempura-diff` でも同じファイルを静的アセットとして配信します（旧 URL の `/tempura-changelog` は `/tempura-diff` へリダイレクトします）。画面用のコピーは作らないでください。

## 1. 目的と非目的

* `diff.md` は現バージョンの機能ガイド（スナップショット）です。`## YYYY-MM-DD の変更` のような日付別の変更履歴は書きません。
* 時系列の変更履歴は GitHub Releases や git 履歴へ委ねます。`CHANGELOG.md` は明示的な依頼がない限り編集しません。
* バージョン番号は `diff.md` に手書きしません。画面では `package.json` から生成されるクライアントのビルドバージョンを `@@/js/config.js` の `version` から自動表示します。バージョンを上げる際に文書の番号を合わせる作業は不要です。
* 対象読者は前半が一般ユーザー、後半がサーバー管理者・モデレーターです。開発者向けの設計・手順・テスト構成は対象外とし、`docs/contributing/` に書きます。

## 2. 掲載の採否基準

対象読者は前半の一般ユーザーを第 1 優先、後半のサーバー管理者・モデレーターを第 2 優先とし、開発者は対象外とします。

掲載するかどうかは統合先ブランチの実装を確認したうえで、単一の基準「行動変化テスト（本家との違いの理解・導入判断・設定操作が変わるか）」で決めます。未マージの実験や取り消した変更は書きません。本家にもある機能は Tempura 固有の違いがある場合だけ書きます。

仕様や制約が変わった機能は追記せず既存の項目を書き換え、廃止した機能や本家へ取り込まれて独自差分がなくなった機能は削除します。

| 変更の種別 | 掲載 | 扱い |
| --- | --- | --- |
| 独自新機能 | 書く | 操作主体に合わせて一般ユーザー向け（前半）または管理者向け（後半）の該当カテゴリへ追加します |
| 本家拡張差分 | 書く | 本家 Misskey の機能と挙動・仕様が異なる点だけを該当カテゴリに書きます |
| 設定・権限 | 書く | 新設・変更されたユーザー設定、管理者設定、ロール権限を該当カテゴリに書きます |
| UI 配置変更 | 条件付きで書く | 画面構成やメニュー位置の変更で、利用者の操作手順や設定経路が変わる場合だけ既存項目を書き換えます |
| バグ修正 | 書かない | 本来の仕様どおりに戻しただけの修正は GitHub Releases へ委ねます（仕様や制約自体が変わる場合は既存項目を書き換えます） |
| セキュリティ内部対策 | 書かない | 利用者や管理者から観測できない内部防御（OAuth2 LRU、WebAuthn `GETDEL` 等）は書きません（設定や可視挙動が変わる場合だけ書きます） |
| パフォーマンス最適化 | 書かない | 体感や操作手順が変わらない内部最適化やリファクタリングは書きません |
| CI・Storybook | 書かない | テスト、CI、Storybook、Chromatic などの開発者向け変更は `docs/contributing/` へ分離します |

## 3. カテゴリ体系と SSOT 配置ルール

230px のサイドバーに 1 行で収まるよう、カテゴリ名は日本語 13 文字以内を目安にします。前半を一般ユーザー向け、後半をサーバー管理者・モデレーター向けとした推奨 9 カテゴリ構成を使い、互換性や利用上の共通注意はカテゴリ末尾へ分散せず冒頭の `注意事項` に集約します。

| 番号 | カテゴリ名 | 位置づけ |
| --- | --- | --- |
| 01 | `はじめに：主な特徴` | 先頭導入。5〜6 本柱の概念ガイドとカテゴリ案内のみを書きます（個別機能名・数値・設定キーは禁止） |
| 02 | `プライバシー・公開範囲` | 一般ユーザー向け（前半） |
| 03 | `ノート・TL・検索` | 一般ユーザー向け（前半） |
| 04 | `アンテナ・フォロー・通知` | 一般ユーザー向け（前半） |
| 05 | `AI・LLM・翻訳` | 一般ユーザー向け（前半） |
| 06 | `見た目・ウィジェット・遊び` | 一般ユーザー向け（前半） |
| 07 | `管理：登録・認証・匿名保護` | サーバー管理者・モデレーター向け（後半） |
| 08 | `管理：モデレーション・権限` | サーバー管理者・モデレーター向け（後半） |
| 09 | `管理：連合・外観・運用` | サーバー管理者・モデレーター向け（後半） |

### 1 機能 1 か所の配置ルール

同じ機能を複数のカテゴリへ重複して書かず、1 機能につき 1 か所だけに本文を置きます。配置先は次の 3 段階で決めます。

1. 操作主体: 一般ユーザーが使う機能は前半、サーバー管理者・モデレーターが設定・運用する機能は後半に分けます。
2. 必須前提: 利用や有効化に特定の機能群が必須前提となる場合は、その前提を担うカテゴリに置きます。
3. 初回操作場面: それでも複数カテゴリにまたがる場合は、利用者が最初に操作・探索する場面のカテゴリに本文を置きます。

複数カテゴリにまたがり導線が衝突する数件に限り、もう一方のカテゴリに `詳細は「〇〇」を参照` の 1 行ポインタを置けます。`〇〇` には実在する `##` 見出し名と完全一致する名称を書き、ポインタ行に詳細な仕様の語句や否定表現は重ねません。`上記参照` や `下記参照` のような位置に頼る表現は、検索やカテゴリ単体表示で文脈が切れるため禁止します。

## 4. 1 機能あたりの形式・記述粒度

### 基本形式と超大型機能の例外

* 基本は 1 機能につき親項目 1 行（`* **機能名**: 何ができるか・本家との違いと利用場所。`）を置き、子項目（半角空白 2 個 + `* `）で目安 0〜3 行（上限 4 行）に収めます。子項目には前提・権限・主な設定・可視仕様境界（バグ誤認、データ損失、プライバシーに直結する仕様上の制約や上限）を書きます。
* `使い方:` や `設定場所:` のような固定スロットラベルの反復は検索ノイズになるため避け、自然な日本語で書きます。
* 検索フィルタは親項目ごとに一致を判定するため、1 つの機能を兄弟の親項目へ分割すると検索時に概要が抜けます。
* どうしても 1 親項目に収まらない超大型機能に限り、`### 機能名` の直下に通常文で 1〜2 文の共通概要段落を置き、その配下に独立したサブ機能を親項目 `* ` で並べます。画面の検索は項目一致時も同じ小見出し内の段落を保持するため、概要が落ちません。

### 文体・UI 経路・識別子ルール

* 文体は敬体（です・ます調）に統一し、文末に句点「。」を付けます。
* 1 項目 1 行・1 段落 1 行で書き、日本語文を途中で物理改行しません。日本語を含まない英数字だけの項目も書きません。
* UI 経路は「画面＋大グループ（または 5 カテゴリ名）」の 2 階層までに統一します（例: `設定 → 独自機能（AIと通知）`、`コントロールパネル → 設定 → 独自機能（登録・参加制御）`）。末端の細かい項目名は画面変更でずれやすいため省きます。
* Vue コンポーネント名、ファイルパス、設定キーの羅列、管理 API 名、内部定数は禁止します。ロール権限 ID、画面 URL パス、公開範囲値の 3 種に限り、日本語表記の末尾に括弧と単一バッククォートで任意に併記できます（例: パブリック投稿（非LTL）の許可（`canPublicNonLtlNote`）、Misskey-Tempura の独自機能（`/tempura-diff`）、パブリック（非LTL）（`public_non_ltl`））。

### 記載しない内容

次の内容は実装変更で陳腐化しやすく、読者の理解を妨げるため書きません。

* タイムアウト秒数、リトライ回数、HTTP ステータスコードの列挙、内部キャッシュ容量
* 設定の選択肢の全列挙
* Vue コンポーネント名、ファイルパス、設定キーの羅列、管理 API 名、内部定数
* 相対時間表現（`このバージョンで`、`この変更より前`、`前回のリリース`。なお「直近 24 時間」のような機能仕様上の期間表現は対象外です）
* ハードコードした件数（`26 項目` など）
* バージョン番号の手書き
* 日本語文の物理改行による途中折り返し

## 5. 対応書式・MFM 安全ルール・配信の仕組み

GitHub とアプリ内で同じ内容を読めるよう、次の書式だけを使います。アプリのパーサーは Markdown 全体を解釈するものではありません。

| 書式 | 用途 |
| --- | --- |
| `# 文書名` | 文書全体のタイトル。画面の見出しには専用の翻訳を使います |
| 最初の `##` より前の通常文 | 画面冒頭の導入文。1 段落（1 行）のみで書き、空行で複数段落に分けません |
| 単独行の `注意事項` と、その後の `* ` | 折りたたみ式の注意事項。箇条書きのみを 1 項目 1 行で置きます |
| `## カテゴリ名` | カテゴリ切り替えと検索結果の見出し |
| `### 小見出し` | カテゴリ内のまとまり |
| `* 説明` | 機能の項目（`*` の後ろは半角空白 1 個。タブ不可）。件数はこの階層を数えます |
| 半角空白 2 個 + `* 補足` | 直前の項目の補足（字下げは半角空白 2 個のみ。全角空白・タブ不可）。入れ子は 1 段までにします |
| `<!-- コメント -->` | 保守用メモ。表示・検索の対象外です |

冒頭の導入文は 1 段落（1 行）のみとし、空行で複数段落に分けません。カテゴリ内の通常文は空行で段落を区切り、各段落を 1 行で書きます。画面では小見出しの下・箇条書きの前に表示されるため、箇条書きの後に段落を置かないでください。導入文・カテゴリ内段落・`注意事項` はプレーンテキストで描画されるため、バッククォートや `**` は使いません。

`####` 以降の見出し、`- ` や `+ ` の箇条書き、番号付きリスト、Markdown 表、コードブロック（チルダフェンス `~~~` を含む）、ブロック引用（`> `）、生 HTML タグ、水平線は使わず、通常文と箇条書きに直してください。箇条書き記号の後ろの区切りは半角空白 1 個（タブ不可）、子項目の字下げは半角空白 2 個（全角空白・タブ不可）とし、入れ子は 1 段までにします。3 段以上のネスト、親項目のない子箇条書き、`注意事項` 内の子箇条書き・継続行・箇条書き以外の行は使いません。重複する `##` 見出し、同一カテゴリ内で重複する `###` 見出し、項目も段落もない空の `##` カテゴリと空の `###` 小見出しは禁止します。旧 URL の `/tempura-changelog` も本文には書かず、`/tempura-diff` を使います。コメント内にも認証情報や非公開情報は置かないでください。

### MFM 安全ルール

カテゴリ内の箇条書き（`* ` と `  * `）はアプリ内で `<Mfm>` として描画します。意図しない自動リンクや装飾崩れを防ぐため、次のルールを守ります。

* 許可する MFM 要素は通常テキスト、太字（`**...**`）、単一バッククォートのインラインコード（`` `...` ``）、Unicode 絵文字、URL、外部リンク（`[文言](https://...)`）だけです。
* 二重バッククォート（`` ``...`` ``）と相対 Markdown リンク（`[文言](/tempura-diff)` 等）は MFM で解釈されないため禁止します。
* 行末の「半角空白＋`検索`」は MFM の検索ボックスとして解釈されるため禁止します。
* メンション（`@user@host`）、ハッシュタグ（`#tag`）、カスタム絵文字記法（`:word:`）、MFM 関数（`$[...]`）、斜体、取り消し線、`<small>`、`<center>`、引用（`> `）は本文に出しません。記号そのものを説明する必要があるときは単一バッククォートで囲みます。
* `packages/frontend/src/utility/tms/rj-number.ts` の自動リンク対象（`sm9` などの動画番号、`CVE-...`、`RJ...`、40 桁 16 進数など）はそのまま書くと外部リンクになるため、記載するときは単一バッククォートで囲みます。
* コメント開始記号（`<!--`）を本文で説明する場合は、単一バッククォートで囲みます。インラインコード内の記号はコメントとして除去しません。

### 配信の仕組みと設計理由

本文を JavaScript に埋め込まず、Vite の `?url&no-inline` で内容ハッシュ付きの独立した静的アセットとして出力します。クライアントにはその URL だけを含め、`/tempura-diff` を開いたときに取得します。通信の上限は 10 秒です。取得中は読み込み表示、失敗時は再試行ボタンを出し、ページを離れたら通信を中止します。

GitHub raw の `develop` を直接取得すると、古いバージョンのサーバーにも未対応の機能を表示してしまいます。同じビルドのアセットを参照すれば、画面と説明のバージョンが一致し、閲覧のために GitHub へ接続する必要もありません。

更新時はフロントエンドを再ビルドし、生成した JavaScript と静的アセットを一緒に配信してください。サーバー上のソース `diff.md` だけを差し替えても、配信済みの内容は変わりません。独自のアセット配信設定を使う場合も、この Markdown を配信対象から外さないでください。

## 6. 更新と確認手順

1. 統合先ブランチの実コード、コミット履歴、`locales/ja-JP.yml` を読み、機能名・画面上の日本語ラベル・設定場所・制約を照合します。
2. `diff.md` を更新します。対応書式や検証ルールを増やす場合は、`packages/frontend/src/utility/tempura-script/feature-catalog.ts`、`packages/frontend/src/utility/tempura-script/feature-catalog-lint.ts`、テスト、この文書もあわせて更新します。
3. `pnpm --filter frontend test test/unit/tempura-script/feature-catalog.test.ts` を実行し、取り込み・入れ子・検索・コメント除外・構造・MFM の各検証が通ることを確認します。UI やルーティングを変更したときは、`test/unit/tempura-changelog.test.ts` と `test/unit/tempura-diff-route.test.ts` もあわせて実行します。`diff.md` 単体の PR でも `.github/workflows/feature-catalog.yml` でカタログ検証が自動実行されます。
4. UI やパーサーを変更した場合のみ、実画面で `/tempura-diff` と旧 `/tempura-changelog` からのリダイレクトを開き、カテゴリ切り替え、別カテゴリの語句検索、狭い画面の表示、取得失敗時の再試行を確認します。
5. コードを変更した場合は、`AGENTS.md` と `shipping-misskey-change` の検査を通します。
